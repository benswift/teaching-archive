## Change of Plans

At the end of last week, I was able to connect the ESP32 board to my laptop via Wifi and mentioned my plan for this week would be to send data to the laptop using the WiFi connection. However, I realised that this is not entirely feasible, as the PS Band would require internet connection to transmit data, which cannot be guaranteed in the type of environment the Band is meant for. It is *doable* by using your phone as a personal hotspot but still extremely inconvenient.

## Interrupt

I managed to trigger an interrupt on GPIO pin 5 by sending data via GPIO pin 18 by modifying the code given to us.

![Interrupt](/images/posts/chinmay/Week9interrupt.png)

Afterwards, I tried to trigger an interrupt using the alcohol sensor which turned out to be more troublesome. As it only has one pin, which is used to send the sensor data (which I'm assuming is quite small voltage), it is not enough to trigger an interrupt and hence we could not read the data.

To solve this, Adi and I discussed using a timer which triggered an interrupt every 30 minutes and notify the user to breath into the sensor. This could work but I disliked not having the device ready whenever the user wants to take a reading. For e.g. if the band notifies the user to breath into the sensor but for some reason the user misses the time window but wants to take a reading 5 minutes later, they would have to wait until the next notification, which does not make for a great user experience.

Therefore, I want to use a physical button as well. Upon pressing the said button, an interrupt will be triggered and the board would start reading the values from the sensor and start sending it to the phone for a few seconds. When the data is sent to the phone, the Band goes to sleep to preserve energy until the next time the button is pressed or 30 mins has passed, whichever one is earlier

## Bluetooth

Bluetooth is a much better alternative. So that's what I focused on this week - trying to establish a bluetooth connection between ESP32 and my phone. I had guessed it would be similar to connection the board via WiFi but boy was I wrong...

I was planning on using [GATT](https://learn.adafruit.com/introduction-to-bluetooth-low-energy/gatt) (Generic Attribute Profile) to transfer data between the two devices. An important feature of GATT is that conenctions are exclusive. This means a BLE peripheral can only be connected to one central device, such as a smartphone, at a time. As soon as the peripheral connects to the phone it will stop being discoverable to the other devices until the existing connection is broken. This is perfect for the PS Band as it only needs to connect to its user's phone and ensures no one else tries to connect to your band and also improves overall security.

First, I tried to connect two boards together, where one acted as the GATT Server and other as a GATT Client. This was fairly straightforward, and the resulting connection was always quick and responsive.

Then I tried turned off the board with the GATT server and ran the GATT client hoping to discover the board on mine and Adi's laptop and/or phone. Nothing. Maybe our devices didn't support GATT? After a quick internet search, I found all our devices support upto Bluetooth 4.0 and 4.2 which should be compatible with GATT. After running the GATT client a few times, we see it finally connect to something. Success!

Adi and I excitedly turn over to the terminal screen to see what finally connected. To our surprise, it was his bluetooth headphones (named The Possum).

![Headphones connected to board](/images/posts/chinmay/Week9Headphones.png)

Even though it was the last device there we wanted connected to the board, it was still progress. Now only if we can replicate the connection to our phones...

After searching through internet for quite a while for any guides or hints which would enable us to connect the board to the phone, we came up empty. To cover all our bases, I try to run BT SPP initiator on the board which is older Bluetooth (Bluetooth 2.1) and less efficient for our purposes. Surpringly, all our devices were now discoverable by the board. Maybe the problem was our devices did not support GATT after all?

![Devices show up on BT SPP](/images/posts/chinmay/Week9BTSPP.png)

Not wanting to give up just yet, we kept trying to come up with a way to use GATT. We finally stumbled upon an app called [nRF Connect](https://itunes.apple.com/us/app/nrf-connect/id1054362403?mt=8) which enables our phones to scan and explore devices with Bluetooth 4.0+. Adi and I both downloaded the app on our phones and tried GATT client on the board once again. We opened the app the see if there was anything there but to our dismay, still nothing.

I then tried to use the board as a GATT server instead of a client and we both refreshed our apps. The board was finally discoverable and there was a button next to it inviting us to connect to the board!

![Board discoverable on phone](/images/posts/chinmay/Week9phone.jpg)

After we connected to the board, we sent some text using the phone to the board. The terminal (which was used to monitor the board) converted the text to ASCII values and printed them! After. There were two channels available for us to communicate with. We tried both.  The first channel consisted of value "0xdeedbeef" and the second channel consisted of value "0xdeadbeef" stored on the laptop. We requested data using the app and viola the phone recevied the data over Bluetooth using GATT!

![Receiving data on phone](/images/posts/chinmay/Week9Data.jpg)

We are finally able to receive data from the board to our phones using energy efficient Bluetooth. However, we still need to be able to implement nRF's BLE functionality into our own app (which we need to start developing soon) which seems like a non-trivial task but hopefully we will manage.
