Pretty sweet, no? It's all written in real-time. Now imagine this happening in a performance setting, with an audience or perhaps in a club. Wouldn't it be great if the audience could take part in modifying components of code remotely? I think it would make the listening exprience far more engaging. Or maybe certain parameters of the code could change as the temperature or amount of movement in a club rises and falls. This makes the live coding performance a multi-agent system; the programmer and the audience have control over the output. It's likely such a design would have only one or a small number of remote controls for the code parameters. Each controller would have to be associated with a disjoint set of parameters so that there won't be any conflicts e.g. two controls try to modify the same parameter in the code at the same time. I think it's also important that the mappping between the data collected from the sensors (touch, heat sensors) is done in such a way that the overall musicality of the performance isn't compromised.

Involving the audience is one of two ideas I have at this stage. The other idea involves bringing an AI agent into the performance. I envision the agent as more of a helper than an adversary to the live coder. For example, if the live coder gets in a bit of a creative rut during their performance (maybe during a long gig), they could allow an AI agent to suggest code structures to use to enhance the performance. If, for example, a melody line in the song was getting a bit stale, the live coder could request changes to the melody line from the AI agent to which it will respond with example code structures the live coder can use. Or the AI agent could also excute the code directly. We can sweep the details under the carpet for now, but the main point is that we need to establish annd manage communication between the agent and the live coder.

Though this communication can be coded live by opening a UDP socket and writing and sending message on the fly, I thought a remote control would be perfect to trigger communication from the live coder to the agent since it can be done through the press of a button. This way, the collaboration between the coder and the agent is made more efficient. What would be even cooler is if the coder could change some parameters of the AI model; parameters which control the 'conventionality' of its output.

As you probably saw, Ben would write functions (or closures) to manipulate a digital signal by creating and changing pitch and ryhthm. This information appears in the form of lists. In this video, Ben is using a runtime environment called Extempore. They recently released a new feature called patterns.
Essentially, patterns are just lists. If we have a midi pitch list which represent the bassline of 'Money' by Pink Floyd, it would look like this.

<p style="text-align: center;">
[B, B, F#, B, F#, A, B, D, B].
[35, 47, 53, 47, 41, 44, 46, 49, 35]
</P>
And here is its use in a pattern.
<p style="text-align: center;">
(:> A 4 0 (play syn1 @1 80 dur) (list 35 47 53 47 41 44 46 49 35))
</p>
Patterns allow you to apply transformations to these lists in a fairly compact way
With my experience live coding so far, I know that I tend to be overwhelmed with the ammount of code I need to write under the time pressure of the performance so, I thought
it could be useful to have an AI agent which had control over one component of the music.
So, I am currently working on integrating an AI agent into the live coding environment so that, if the programmer was ever in a creative rut, they could request some input from the agent which would take control of say the bassline or melody and develop as the song progresses. I'm currently implementing a Markov Chain as the base model for my agent. This is a stochastic model which transitions between states conditioned on the immediate previous state. In this example, the 'states' which the model transitions between are various functions which can be applied to the pitch list. For example, one function which could be applied to the list is a reversal or a retrograde. The model is represented by a probability Matrix. So the ijth element is the pobability that after the ith function is applied to the list, the jth function is applied to the list. I am planning to set the values myself, by a trial and error or by following some general rules in music.

Okay thanks for bearing with me. Here's where I'm seeing the IoT component coming in. There is this notion in machine learning called temperature. Essentially, the predictive capabilities of the agent., in this case the probabilities in the matrix, can be controlled by the temperature. This is a control of how weird the predictions are. e.g. In our Markov chain, upon initial setup these probability values will be initialised to values which make the most sense musically. So if we want to spice it up a bit, we can give the musician control over these probabilities, they can control how unconventional the transitions are. This could also control the e.g. conventionality of timbres. This could be done by connecting a touch pad or some sort of control which can change the probability video.
