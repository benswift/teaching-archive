The quest continues to design an IoT device(s) that distributes agency in a live coding performance. How can we bring control to the audience so that they can engage more with the code generating the music? Is it possible to involve an AI agent in a live coding performance without taking the control away from the coder? How can we give a live coder the control over the conventionality of the music generated by the agent? If you're new to this blog, see [last week's post](https://cs.anu.edu.au/courses/china-study-tour/news/2018/11/30/h-f-f-c-t-s/) to get you up to speed.

### Making a thing which lets an audience internet

[![IMAGE ALT TEXT HERE](https://img.youtube.com/vi/G1m0aX9Lpts/0.jpg)](https://www.youtube.com/watch?v=G1m0aX9Lpts)
Here's the thing...
A live coding gig usually involves some kind of visual aid e.g. a projection of the programmers code onto a screan, or sometimes one coder creates the music while another does some live visuals.

For the average Jo/Josephine sitting at a live coding gig, it might not be easy to decipher what the code means or how it relates to the music it produces. I want to see if I can create an IoT device which allows audience members to control some components of the code so that they can walk away with a better understanding of how the code structures generate the music produced. I'm sure that there are some hard-core live coding purists that are twirling their mustaches and cursing at the idea of explaining the code to the audience. And I can see where they're coming from. The enigma behind the fact that a bunch of symbols splattered across a computer screan are supposedly producing/defining
rules which the piece of music they are listening to must follow is a large part of the charm of live coding. It sort of becomes a game of deduction for an audience member.

_Lights start flashing around a piece of code and some drums start thumping. Okay, so that must mean that section of code defines what the drums do. But how are they making the high hat parts so expressive - softer and louder and softer again. 'sin' and 'cos' are peppered through the code, maybe that is making the intensity oscillate?_

You kind of start to build your meaning around what the code represents. Whether their understanding of the meaning is accurate or not, extracting some meaning from the code contributes towards their experience (and arguably their enjoyment of the performance).
Having said that, I think there should be a way to give the audience some control over the code creating the music without having to spell out what each function does. It doesn't have to be a compromise. My first idea was to have some controllers which allow audience members to change parameters in the code which control e.g. the volume/pitch/tempo etc. But, I feel like this will not give the audience much insight into the processes defined by the code which control the way the music is generated. e.g. temporal recursion, quantizing pitch, use of modulus and other mathematical functions ect. At this stage, I'm not sure exactly what kind of interactions will give users a better understanding of the music generation processes. But maybe next week, I'll be able to report back with some ideas.

### The_rhythm_is_gonna_getchu()

I'm not much of a club-goer, but I like to dance. There have been several dissappointing occasions where the DJing at a club has been an abomination. I was one at a club where the DJ would play a song, wait for it to build and just before the beat drops, he would switch to another song. It was a jam filled donut, without the jam - an utter dissapointment. This made me think that it could be useful to have a wearable device (maybe a wristband) which can collect motion data from each member inside a club or on the dance floor and give it to the DJ upon which they can use it to do some analytics about what features in music that trigger more movement. E.g. there could be certain rhythms that make people dance more.
Live coding in a club setting could allow even cooler applications for such a wearable. You could have the amount of motion generated by the wrist-wearables collected and used to increase the tempo or change some other aspects of the music in pseudo-real time. The club-goers could have limited, but direct control over certain parts of the music. Real-time changes to the music will be a bit too drastic though. I'm thinking of aggregating all the motion data from the devices and then mapping the aggregate readings to some value on a scale between minimum and maximum values for e.g. a volume parameters. Another, more advanced, version of this idea is to guage the types of movements of club-goers make and use it to predict what kinds of songs to queue up/play next. You might be able to do this by monitoring either motion data or video data and having a machine learning classification algorithm which is able to classify styles of dance or convert movements to rhythms and have this predict song styles/genres which fit those movements. Obviously I have no idea if there is an algorithm trained on motion to classify styles of dance. If such an algorithm doesn't exist, then creating one is well outside the scope of this project, so... brb, checking github for dance ai classifaction algorithm.

### Let's talk hardware

If I were to create some kind of wearable, I need something small enough to fit on a wristband. The ESP8285 is used widely for wearables. The only functionality I want from the chip or the wearable (smart bracelette) is to send the motion data to some central processor. The chips are cheap so it would be the ideal option if I were to aggregate data from multiple devices. They are manufactured in China and until recently, there weren't detailed English documentation so I'm not sure if the community around these chips will be of much help to me, but I'll see what I can find online. There is an open-source SDK available for ESP based on the GCC toolchain. Unfortunately, the chips only have GPIO pins (16) and no in built accelerometer. So I will additionally need to attach an accelerometer. The MMA7660 seems to be a good choice. It's not too power hungry and there is a fair amount of documentation for its use with the ESP8266. However, it seems like there is a lot of room for the gesture detection stuff to go wrong since you might not be able to assume the motion data collected by the device is purely coming from dancing or it might not indicate that a person is enjoying the music. So, perhaps heat sensors or pulse sensors are a better measure. At this stage I haven't looked into specific sensors at this stage, but hopefully I should have a better idea of what is avaible next week. The ESP8285 and ESP8266 are widely used in the smart-bracelet world so there should be some documention or at least a community around it (_crosses fingers and toes_)
