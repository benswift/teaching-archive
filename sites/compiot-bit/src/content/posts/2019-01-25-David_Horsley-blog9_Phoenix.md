## Phoenix Rising

In last week’s post, I spoke at some length about how it wasn’t a great week in terms of objective results. It wasn’t that I didn’t put the work in, it’s just that it didn’t materialise into anything that I could point to and say “That over there is what I did this week”. Last week was such a lousy week that it even had me questioning if BLE Mesh (which has been a focus of this project for weeks) was ever going to work for our project - so I borrowed an idea from the world of mountaineering and declared a ‘Turnback Time’ (or a deadline, if you’re not feeling so inspired). An apt analogy perhaps, considering the mountain of work that seemed to lay ahead of us. But looking back now it looks like more of a volcano than a mountain; it was still a pain to climb, but amongst the fire and brimstone, from the ashes of last week has risen a mighty phoenix.

![Volcano](https://media.giphy.com/media/va72nn4rrafGo/giphy.gif)

But getting to the point, the fact remains that this week has been a productive and successful one for me when it comes to this project. After pouring a seemingly endless amount of time into understanding BLE Mesh, it finally feels like it’s starting to pay off. For some background, up until this week, most of my work had been focused on a few examples of BLE Mesh that have been included in the beta for the ESP-IDF BLE Mesh code, and I spent hours painstakingly going through the code line-by-line annotating it in order to understand what was going on. This problem was compounded by the fact that I wasn’t using an IDE or even a fancy editor, because everyone seems to recommend starting with a basic text editor when you’re first starting out with C (which I more-or-less am). But while I’m sure this is a great way to learn C right from the very beginning when you start by writing simple programs, it left me feeling woefully unequipped while I’ve been dropped into the middle of a huge program that hooks into a seemingly endless library.

The thought of using a more helpful editor or IDE had actually crossed my mind a few weeks ago, and after digging through forums with hundreds of Greybeards preaching the gospel of text-editor and command-line and saying how their first C compiler was little more than a pile of sticks and twine, the name VS Code was something I saw being thrown around. But because nothing so far in this project has been easy, there were of course problems with VS Code too. Although I could open my C files and do basic editing, it seemingly couldn’t understand the macros or include statements that were used. This was fixed easily by setting the correct paths to the other files, but this seemed to set off another issue in VS Code, causing complaints about errors in the code, even though it could be compiled and flashed onto the boards successfully. It turned out that this was actually a bug in VS Code itself, but that was an easy fix and I finally had an editor that would support helpful things like syntax highlighting and code completion.

With all this space-age editor technology, I’ve actually managed to get some serious work done. We now have a mostly working system in which one device operates as a Provisioner, adding new devices to the network and distributing keys to allow for secure communication on the network, and also as a Client, allowing it to send and receive messages to other devices on the network. The other part of the system is the Server, which in our case will be the ‘glowsticks', which essentially has some data (aka. “State” in Bluetooth Speak) and will send this data to the Client when asked to do so. Unfortunately, this part isn’t 100% complete yet, and the Server doesn’t always understand what the message says or how it’s meant to respond, but we’re certainly miles ahead of where we were last week. In essence what we’ve done is created virtual Mooseheads: the Provisioner is the bouncer who lets people in, making sure everyone is being good and stopping people sneaking back in pretending to be someone else. The Clients (the bar staff) ask for information by requesting their drink orders from the Servers (glowsticks) and will do different things depending on what data they get back. The Servers hang around waiting to provide information when asked for it and are sometimes confused by seemingly simple things (just like people at Mooseheads). Where we go from here with the BLE Mesh is pretty straightforward, we need the Server to respond correctly all of the time, and for the Client to be able to extract the data from this response and aggregate this data for use in selecting music.

This week we also worked out a few unsolved issues in our project, such as exactly how the music would actually be played. We’re now learning towards using a Raspberry Pi, running Raspbian (a special Linux distro) to simply stream the music using a web browser. This also sidesteps the issue of the ESP32 boards lacking a headphone jack as these are built in components of some Raspberry Pi boards. Today marks exactly one month out from our final exhibition, which is quite frankly terrifying. It’s terrifying not necessarily because I don’t think we’ll get it done in time, but rather because it seems like it would be very easy to cruise through the next few weeks without much thought and end up in a poor position in terms of our project. I think that completion of this project, according to our early plans is still possible in the next month, but in order to do it we’re going to have to stay focused and constantly be pushing towards the next goal.
