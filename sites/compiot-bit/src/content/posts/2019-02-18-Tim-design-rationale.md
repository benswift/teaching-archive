### what ideas or existing projects inspired your work?
From the start, my partner Harry and I wanted to do something decentralized or distributed. He’d enjoyed taking the Systems Networks and Concurrency course previously so that was something that he wanted to continue doing and that I was also interested in exploring further. 

The first idea we had for the project was a series of sensors to help monitor flora growth whilst feeding data back to a server. Whilst we were in China I heard about the [Great Green Wall project](https://en.wikipedia.org/wiki/Great_Green_Wall). The Great Green Wall was an anti-desertification effort in which large amounts of trees and flora was planted along the Sahara Desert in Africa in order to stop the spread of the desert. Our original idea for the project was to make a series of devices connected in a large mesh network over a large area communicating with each other and relaying data to monitor the growth of trees in the green wall. A more general application of this would be to setup a network of devices to monitor the growth of crops on farmlands. These devices would contain sensors and collect data for things like light/UV level, humidity, soil pH, CO2 levels, temperature and more. They would then be placed along the area to be collect data. They would then pass the data they collect along through each other to a central control node which would also be used to issue commands across the network. However, after discussions with Ben & Kieran and our desire to focus on the decentralized nature of the devices over the sensor part, he suggested switching our focus to something which focused on showing how devices in a mesh network communicate rather than the farm sensors.

Our current and final project took the mesh network from the previous idea and focuses on connecting multiple microcontrollers together in to simulate the network connections that IOT devices could have to each other, then using LED strips between the controllers to show the messages being sent between them. Each controller would emulate a network connection or smart device in the network. The primary focus would be to show when and how the devices communicate with each other using the distance vector routing algorithm to figure out where each device is in the network as well as figuring out when a device is disconnected, showing how all the devices could link together. We took inspiration from Will Cashman’s work (link) using the STM32F103 based Black Pill (link) microcontroller and LED strips to highlight live coding musical performances. We were going to use the same Black Pill boards as they were cheap, whilst having enough functionality for what we wanted to do. They were also ARM M3 based and we’ve had experience with a different ARM M4 board so that would make things a bit easier to work with.

### how does your project explore the theme and what do you want the viewer/user to think/feel/do after they’ve experienced your artefact?

The project also fit the theme of “(dis)connecting together” through helping viewers appreciate an aspect of IoT that most consumers don’t think about, the interconnectedness of a larger network of devices. Usually when most people think of IoT they think about the devices used in an IoT network rather than the network itself. The distance vector routing algorithm used was the original routing algorithm used when the internet was first built and while not a prevalent, is still used today. This project should help viewers visualize how devices connect across the internet and gain a greater appreciation for how devices in an interconnected world can communicate even if they can’t communicate directly with the device they want. However, while the distance vector algorithm is still used today, there are various other routing algorithms that are commonly used such as Link State Analysis protocols. As such while the project gives a visual representation of one type of routing algorithm, it does not represent all the types of communication that occur on the internet.

### what design criteria did you choose to prioritise? which criteria did you have to sacrifice?

When we were planning the final iteration of the project, we had a longer list of things we wanted our project to do. These included:

1.	Lighting up the LED strips as messages are being passed between boards
2.	Having a button to turn boards on/off to simulate devices disconnecting and reconnecting to the network
3.	Having each microcontroller in the network be accessible from a laptop connected to a particular node and be able to send a message to turn any board’s LED
4.	Be able to send signals to have sets of boards in the network react (to simulate events such as turning on all the smart lights in a room).
5.	Attach a speaker to a board and send audio data over the network to simulate a smart speaker and have the LEDs react accordingly 

However, after a discussion with Ben in which he stated that some of the criteria seemed superfluous, we decided to focus primarily on criteria 1 and 2 and highlight the distance vector algorithm. Criteria 3-5 focused on adding features that the network could do and not at showing how the network worked and were not necessary to complete the project. 

### what was your design process? how did your project develop over time?

Our idea for the project changed significantly over the last couple of months. While the original idea was developed by discussions I had with Harry, the idea for using the distance vector algorithm came from when I had used it in a previous assignment. The final concept for the project only came about after discussions with Ben & Kieran, and later conversations with them would help to refine the focus of the project to what it is now. Smaller decisions about hardware and what peripherals to use such as using the USART for inter-board communication and which LED strip to use came about in discussions with friends who had more experience than I in working with microcontrollers.

### what were the challenges you faced in developing your ideas and prototype?

Whilst we were in china, we were required to use nesC (a c dialect which hasn’t had a major update since 2012 and doesn’t have great documentation) to build a robotic car. Unfortunately, we really didn’t enjoy doing this and as it was my first experience working with C, we decided that we wanted to avoid C and give rust a go. I had investigated using rust for embedded development previously and there were several crates (rust equivalent of packages) that offered low level api access to hardware peripherals. That combined with the fact that when we were deciding what to use, rust had just released their first stable version, led us to give rust a try. 

Turns out this wasn’t the best idea. On top of having to learn a new language with some programming features that we hadn’t seen before, due to how new and constantly changing the language and tools was, it was sometimes hard to tell which instructions and crates were out of date or not-applicable to the board we wanted to use. There were numerous occasions where I thought I had found example code for getting the USART working only to find out that the code wasn’t applicable to the black pill, or that a crate we wanted to use was deprecated in favor of a different one, but that it hadn’t been noted in the git repo’s readme. Luckily the embedded rust group has an IRC channel where we were able to ask for advice.

Two main peripherals that we wanted to use were the USART for communicating between boards and an Adafruit Neopixel LED strip. While there normally for the USART there are libraries that exist to help use it I was unable to find one in Rust applicable to the black pill. I needed to dig through the reference manual for the board as well as find example code in C online for how to turn it on, then figure out how to translate that into rust. Then the LED strips used a driver called WS2811, which I was unable to even find a C library targeting the black pill to use as reference. However, there was a lot of documentation online for how the protocol worked normally so I was still able to recreate the driver in rust. Rust’s embedded crates also had some odd quirks that weren’t fun to debug, as well as a development environment that was sometimes a hassle to use. I was switching between vscode’s cortex-m debug extension to view peripheral registers and terminal GDB debugging to debug and run my code.

### how has this project changed the way you think about IoT?

Whilst our project was intended to give viewers a greater appreciation for how interconnected devices can be, it instead gave me a better appreciation for how much work goes into making microcontrollers and the software used on them. For the black pill board, the reference manual that I used to figure out how it works is 1134 pages long. Having to dig through in more detail that I’ve needed to before has given me a much greater appreciation for the fact that many people have spent many hours designing, building and writing a thousand-page in-depth and detailed reference manual for a 2.44cm x 5.71cm size board.

Not having access to a lot of pre-written libraries for this project meant that I needed to do a lot of research into writing my own versions. This involved diving through the reference manual to figure out how certain peripherals worked, looking through the Rust documentation online on how to use the peripheral api and finding comparable C code to use as a reference. Whilst there wasn’t always something useful on the rust side, there were a lot of libraries and solutions available on the C side and given the time it’s taken to write my own versions of different libraries, it amazes me how much time and effort has gone into this field. 

It also presents an interesting idea as to where the rust embedded environment could be in a few years. The rust embedded environment has a very active group of people behind it constantly working on improving and expanding it. A Microsoft security engineer has recently come out and said that [70% of bugs in their products are memory related](https://www.zdnet.com/article/microsoft-70-percent-of-all-security-bugs-are-memory-safety-issues/). Whilst that number is most likely higher than the overall average, rust has a lot of features built into it that are designed to make it more consistently memory safe than C. Given that security is such a huge concern when it comes to IoT devices, this feature of rust could become more of a selling point for using the language in the future for creating IoT devices. Espressif also [announced](https://esp32.com/viewtopic.php?t=9226&p=38466) recently that they’ve added Xtensa support to LLVM, meaning that you will soon be able to write and compile rust code for the ESP32 platform which is already greatly used for IoT devices due to their low cost and network connectivity. If the tools for embedded programming in Rust continue to be refined, it could be a very useful language that can address some of the major concerns in the development of IoT devices in the future.
