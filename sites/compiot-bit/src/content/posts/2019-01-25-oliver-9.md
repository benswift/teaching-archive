## The receiver

With the API working (kind of) smoothly, the next task is to build the recevier. In my last post I explained that I have exposed a file `reccomendation-options.json` which serves as inputs for the reccomendation call. These options are derived through a voting algorithm that reads all members of the BLE network and then will distill the information into five genres to be submitted.

Because the ESP32 is not the best device to manage the streaming of music via spotify to the speaker I've come up with two solutions:

### Option 1 - Just do it

![nike logo](./images/oliver-johnson/nike.jpg)

The ESP32 can be networked to interact with the Spotify API. In [Neil Kolban's book](kolban-ESP32.pdf#page=447) he describes in detail how to set up the ESP32 as a REST Client using a mongoose server to send Http requests.

> "_Using the Mongoose APIs, we can quite easily send a REST request and work with the response. The high level story is to initialize Mongoose with `mg_mgr_init()`, request a connection to the REST service provider with `mg_connect()`, associate the connection as being HTTP oriented and then start processing events. The first event to return will be an `MG_EV_CONNECT` event indicating that we are now network connected. From there we can use `mg_printf()` to send the REST request. When the REST partner responds, we will get an `MG_EV_HTTP_REPLY` event and we have completed our request/response pairing._"

This means that the ESP32 can handle the API calls to authenticate and choose reccomendations via the [Web API](https://developer.spotify.com/documentation/web-api/quick-start/). But to stream the music requires implementing the Web Player SDK on a supported browser. This cannot be done as it would require installing an OS that could support either Microsoft Edge or Google Chrome, two beefy web browsers. The ESP32 simply doesn't the onboard resources to handle a distro that could do this.

Instead by directing the ESP32 to manage what song the user is currently listening to it would be responsible for the selection of songs. A user could instead use the spotify application on their phone to stream the music to the speaker.

This however seems to undermine the plug-and-play aspect of the device. It also draws away from the robustness of an IoT system, by having to be dependent on an external application for the core functionality.

### Option 2 - Raspberry Pie

To circumvent the hardware restrictions of the ESP32, we could instead use a Wifi enabled Raspberry Pi. The [Pi Musicbox](http://www.pimusicbox.com/) would be a perfect application as it facilitates the use of spotify Connect. It would provide a real plug-and-play experience requireing the user to give their permission once and then just rely on the refresh token for future authorization (the token expires after an hour).

Moreover an implicit problem in solution one is that it requires the ESP32 to simultaneously operate on the Wifi and BLE networks using the same radio and antenna. With this solution an ESP32 could be wired into the Raspberry Pi to serve as a dedicated radio and antenna avoiding the need to manage contention.

Plus David says he may have one lying around. Implementation wise we can slap [Raspbian](http://www.raspbian.org/) on his pi, install chromium or Music box depending and go from there.

### A solving a solution

We're going to follow this path to provide a smooth experience and a more robust system. I do have reservations though, mainly is that it removes the complexity from the system. Aside from the BLE network that we implemented the station is now mainly an app that we didn't create, plus some API calls and a voting algorithm. It's not incredibly complex and I'm concerned that it doesn't meet the spec. On a system level it becomes much more IaC design with code reuse rather than something very innovative at a lower code leve that could be done with the ESP32.

To offset this less complex implementation I plan on curating a good user experience for the end product: Glowsticks that are easy to operate, the speaker needs almost no setup etc.; and a good gallery exhibition.

## The Gallery

An example of a mood room:

<p></p>

While I haven't taken this approach for inspiration I do want people to get excited over our invention. I want the exhibition-goers to remember our project and talk about afterward. Our purpose, as I've described, is to begin a conversation about collective choice and the current bashful attidutes towards our own music preferences.

To start this conversation I want to give all exhibition goers a chance to experience the voting algororithm of the system.

Here is how I see users interacting with it:

They walk into the exhibition and can take one of a few different genres. (This probably means we need to design a way to quickly change genres as we only have 5 ESP32s to play with). As they are walking around the rest of the gallery they the system will determine what songs to play. we'd have to talk with Ben about letting this happen but it would be cool to let them interact with everyone else while our system promotes a self-determined playlist.

If we couldn't let them roam we'd have to come up with an activity for them to do at our gallery. Maybe we run "Tours" where we take 5 participants, give them a blindfold each, get them to choose their genres and then see how the algorith chooses their music.

> As a quick sidebar, the key "Intelligence" in our system is the Spotify voting algorithm. A potential focus could be to examine how algorithms can control our lives, explored through the trivial example of the Spotify Browse selecting a song.

If that is not very engaging, especially as it is unlikely to be a silent gallery and so it may be hard to focus on just the music, we could give them something to do and see. These activities could be related such as printing out the logs of the system; or unrelated, like hosting a free coffee station that can only be used if you put on the Glowstick.
